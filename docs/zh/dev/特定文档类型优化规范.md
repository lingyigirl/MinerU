# MinerU 特定文档类型优化规范

> **阅读对象**：修改 MinerU 文档识别/表格后处理相关代码的 AI 智能体。
> **来源**：水费发票表格优化实战总结（2026-08）。
> **定位**：本文档是**可执行规范**——抽象原则 AI 无法真正遵守，因此每条原则都包含具体的【AI 执行流程】、【自我检查问题】和【红线】。修改此类代码前必须逐条对照第五节检查清单，并产出第三节要求的分析报告与验证报告。
> 通用编码规范（语言、docstring、日志、最小改动等）见 [.claudecode-rules.md](../../../.claudecode-rules.md)，本文档不重复，只写文档识别优化特有的约束。

## 二、原则详解

### 原则 1：输出不多不少（数据保真）

**一句话**：修改后处理代码后，输出的每个值都必须能在输入文档中找到依据；输入文档中的每个值都必须出现在输出中；值的位置必须有列语义依据。

**案例**：水费发票出现两类违例——"多出"：合计行重复出现数据行的"2148"（空值模式从前一行复制数值）；"丢失"：TH 行缺失"金额"列标题（OCR 拆分字符未匹配关键词）。2026-08 资产负债表再添一类"多出"——"复制"：OCR 补充把已正确输出的半角标签"递延税项:"以全角"递延税项："复制进空的行次列（去重只做同行精确匹配，全角/跨行逃过）。

**填充/回填的三种语义**（回填空单元格前必须先判定，禁止默认"回填=恢复"）：

- **放置（place）**：该字符串（规范化后，全角→半角）在输出中**尚未出现** → 属"恢复 VLM 漏识别"，合法
- **移动（move）**：该字符串 VLM 放错了位置 → 从错位删除 + 放到正确位置，总数不变
- **复制（copy）**：该字符串作为**唯一标签**（分区标题/列标题等）已存在于同行或表头行（规范化后全角/半角一致） → 重复，是多出，必须跳过

判定关键：去重比对必须**规范化 + 覆盖「同行 + 表头/分区标题行」**，不能只「同行 + 精确」——否则全角/半角标点差异与跨行标签逃过去重，正是"递延税项："复制的漏网原因。同时**不得覆盖其它数据行**：单位「吨」、税率「免税」等可合法重复出现的值，若做全表去重会被误拦，导致漏识别单元格无法恢复。

**AI 执行流程**：

1. 修改前保存基线：目标文档修改前的最终输出文件（`*_content_list.json` 或 `*.md` 均可）
2. 修改后运行同一文档，生成新输出
3. 提取表格 HTML 所有单元格值做三层对比：
   - **多出检测**：新输出值集合中的每个值都能在输入 PDF 内容中找到依据；找不到的就是"多出"（如重复的 2148）
   - **重复检测**：唯一标签（分区标题/列标题等）在输出中的出现次数必须与输入一致——已存在于同行或表头行的标签（全角/半角一致）再被回填进空单元格，属"复制"，是多出（如"递延税项："复制进行次列）。可重复值（单位「吨」、税率「免税」）出现多次是合法的，不在此检测范围
   - **丢失检测**：输入 PDF 中存在的值在新输出中都存在。注意**以原始文档为准，不以 VLM 输出为准**——VLM 可能漏识别，不能因为 VLM 没输出就认为值不存在
   - **位移检测**：相同值在修改前后的行列位置一致；不一致时必须给出列语义依据（如"该值在 TH 行的'金额'列下方"），禁止"看起来差不多"的位置移动
4. 每个差异写出解释：该值来自输入文档的哪里、为什么新位置/新状态正确

**自我检查问题**：

- 我这次修改是否**添加**了值？→ 添加的值是"从输入文档读到的"还是"推断出来的"？推断值必须有依据（如从 VLM 拼接格拆分属于"恢复"）。回填/填充空单元格前先判三种语义：**放置**（该字符串在输出中尚未出现 → 恢复 VLM 漏识别，合法）、**移动**（VLM 放错位置 → 删错位 + 放对位，总数不变）、**复制**（该字符串已存在于输出其他位置 → 重复，是多出，必须跳过）。判定必须**规范化 + 覆盖「同行 + 表头行」**比对，不能只「同行 + 精确」，也不得覆盖其它数据行（可重复值会被误拦）；从上一行复制数值属于"推断"，是多出
- 我这次修改是否**删除**了值？→ 删除的理由必须是"该值属于列标题前缀/装饰性文本的一部分"，不是"该值看起来不对"
- 我这次修改是否**移动**了值？→ 移动依据必须是列语义（TH 行标签），不是位置猜测

**红线**：禁止凭空生成输入文档中不存在的值；禁止删除输入文档中存在的值（除非确认属于拼接前缀的一部分）。

### 原则 2：自定义代码隔离（零冲突 Fork）

**一句话**：本项目是 `opendatalab/MinerU` 的 Fork，自定义代码必须隔离在 `custom/` 下，上游合并冲突最小化。

**案例**：`table_utils.py`（约 3800 行表格后处理全套）、`seal_utils.py`（印章 OCR 补充）、`doc_classifier.py`（S1 文档分类）各自独立成模块，上游 `master` 无 `custom/` 目录——零冲突。

**AI 执行流程**：

1. 新函数放入 `mineru/utils/custom/` 下**已存在的对应模块**：表格→`table_utils.py`、印章→`seal_utils.py`、文档分类→`doc_classifier.py`、PDF 处理→`pdf_utils.py`。仅当功能不匹配任何现有模块时才新建文件，并按功能命名
2. 上游文件（`custom/` 之外）只允许 `try/except import + 单行调用`，注释标 `[自定义]`。参考 [vlm_middle_json_mkcontent.py:63-64](../../../mineru/backend/vlm/vlm_middle_json_mkcontent.py#L63-L64) 的 hook 模式
3. 修改完成后检查 diff：非 `custom/` 文件的改动行数应是个位数（仅 hook 调用），且全部带 `[自定义]` 注释标记

**红线**：禁止在上游文件中写业务逻辑；禁止修改上游函数的原有行为（除非通过 hook 注入）。

---

### 原则 3：框架化设计，拒绝特例

**一句话**：分支条件必须是可泛化的结构/内容特征，禁止针对具体文档硬编码规则。

**案例**：`_has_concatenated_data_cells`（[table_utils.py:2925](../../../mineru/utils/custom/table_utils.py#L2925)）用"单元格是否关键词前缀 + 多个数值拼接"这一**结构特征**判断 VLM 单行拼接格式，对任何发票文档都成立；`_INVOICE_HEADER_KEYWORDS` 词典驱动表头匹配，新增标签只需扩展词典。

**AI 执行流程**：

1. 写分支条件前自查：条件中是否出现了**文档名、表号、页码、具体日期、具体数值**？出现即违规
2. 分支条件使用两类可泛化特征：
   - 结构特征：如"表格是否有 TH 行"、"单元格是否拼接多个数值"
   - 内容特征：如"值是否匹配数据类型"（`_is_data_value`）、"文本是否 ∈ 关键词词典"
3. 匹配用**词典/关键词表**驱动，不用 if-else 链逐条硬编码
4. 新功能接入现有管线（`_format_embedded_html` 的 6 步 hook 链），不开旁路专线

**自我检查问题**：换一张没见过的同类文档，这条规则还成立吗？把当前文档名从条件里删掉，代码还能工作吗？

**红线**：禁止 `if doc_name == "某水费发票"` / `if page_idx == 4` / `if table_id == 3` 式特例。

---

### 原则 4：强约束启发式，宁可少修不可错修

**一句话**：任何启发式规则必须能一句话说清"在什么条件下必然正确"；说不清就收紧条件或放弃；修不动的输入保持原样。

**案例**：

- 正面：`_merge_split_header_chars`（[table_utils.py:2999](../../../mineru/utils/custom/table_utils.py#L2999)）合并 OCR 拆分的单字（"金"+"额"→"金额"），约束条件三重：两个都是单 CJK 字符 + 合并结果 ∈ `_INVOICE_HEADER_KEYWORDS` + 仅合并一次
- 反面 1：曾用"合计"关键词检测汇总行——普通数据行含"合计"文本时误触发，被迫改为数字位数启发式
- 反面 2：空值模式仅凭"孤立合计格"就触发（`_find_isolated_summary_cell` 返回 0），缺少"合计不在标准位置"这一约束——这正是空值模式 bug 的直接原因

**AI 执行流程**：

1. 写任何启发式规则前，先用一句话写出：**该规则在什么条件下必然正确**。写不出 → 条件不够强 → 收紧或放弃
2. 启发式 = 特征检测 + 已知词典双重确认（例：单字 × 合并后 ∈ 关键词表）
3. 规则匹配失败的输入必须**原样保留**（fall through），禁止按猜测处理
4. 构造最小反例测试：把"看起来像但不是"的输入喂给检测函数，确认不触发

**自我检查问题**：我的检测条件会不会误触发？检测失败时会发生什么（必须是"保持原样"）？

**红线**：禁止"尽力而为"式修复——修对了是意外，修错了是常态。

---

### 原则 5：多代码路径全覆盖

**一句话**：同一内容可能走多条代码路径，修改前必须画出路径矩阵，每条路径都要有测试文档。

**案例**：同一张发票表至少两条路径——OCR 重建路径（VLM 单行拼接 → `_rebuild_merged_rows_from_ocr`）与非 OCR 路径（VLM 多行直通）。之前"输出不多不少"审计只测了合计行含 ¥ 值的发票：`_find_isolated_summary_cell` 返回 None → 空值模式从不触发 → 漏掉干净合计行的发票（触发 → 破坏）。

**AI 执行流程**：

1. 修改函数前，grep 全部调用点，列出每条调用链
2. 对每条路径写出**触发条件**（什么输入特征走这条路）
3. 对每条路径找到或构造测试文档；找不到的**明确标注"未覆盖"**，不许假装覆盖
4. 修改后逐路径验证

已知路径矩阵（发票表）：

| 路径 | VLM 输出特征 | 触发分支 | 测试文档 |
|------|-------------|---------|---------|
| OCR 重建 | 单行拼接、多数值合并 | `_has_concatenated_data_cells` = True | 单行拼接发票 |
| 非 OCR 直通 | 多行分离、干净合计行 | 拼接检测不触发 | 多行分离发票 |
| 已有 TH 直通 | VLM 自带完整 TH 行 | `table.find("th")` 分支 | 自带 TH 行发票 |

**自我检查问题**：我测试的文档走的路径，和出问题的文档走的是同一条吗？有没有路径没有任何测试文档？

---

### 原则 6：管道顺序意识

**一句话**：后处理步骤有顺序依赖，新增步骤必须检查与前后步骤的交互，防止修复被后续步骤覆盖。

**案例**：`_format_embedded_html` 管道（[vlm_middle_json_mkcontent.py:59](../../../mineru/backend/vlm/vlm_middle_json_mkcontent.py#L59)）顺序为：

```
split_merged_table_cells → split_summary_from_data_cell
  → extract_column_header_prefixes → normalize_invoice_table
  → fix_summary_row_yen_position → split_info_cell_multiline
```

`normalize_invoice_table` 的 colspan 重排（`_format_summary_row_colspan`）改变了列索引，使之前在 `extract_column_header_prefixes` 中做的 ¥ 列对齐失效 → 被迫新增 `fix_summary_row_yen_position` 作为**最终步骤**重新对齐。

**AI 执行流程**：

1. 新增后处理步骤时，列出管道全部步骤及顺序
2. 对每个前后步骤回答两个问题：它的输出会改变我的输入吗？我的输出会被它改变吗？
3. 特别检查**会重排列/行结构的步骤**（colspan/rowspan 规范化、行列拆分）——它们会改变列索引，使之前的列定位失效
4. 插入位置规则：**结构重组之后、最终渲染之前**；依赖列语义的操作（如 ¥ 对齐到"金额"列）放在所有 colspan 规范化之后

**自我检查问题**：有没有后续步骤会重新组织我刚修改的内容？我的修改依赖的列索引，会被前面的步骤改变吗？

---

### 原则 7：根因分析优先（数据流追踪）

**一句话**：先定位"异常是哪个步骤引入的"，再决定改哪里；禁止根据最终输出猜原因直接打补丁。

**案例**："金额"丢失，最初假设"VLM 模型非确定性"——被同模型同输入的多次运行结果一致所证伪（确定性差异，非随机波动）。通过 middle_json 逐步骤追踪才确认：`_has_concatenated_data_cells` 判定触发 OCR 重建 → PaddleOCR 在小图上拆分"金额"为"金"+"额" → 单字不在 `_INVOICE_HEADER_KEYWORDS` → TH 行该列为空。

**AI 执行流程**：

1. 取 middle_json 中 VLM 原始输出（`preproc_blocks` 的 `html` 字段）
2. 逐步骤运行后处理管线，比对每步的输入输出，定位**异常引入的确切步骤**——错误可能出现在完全意料之外的环节
3. 用 logger.debug 日志确认实际执行了哪个分支（"OCR 重建确实执行了"是证据，不是猜测）
4. 写出数据流定位报告后再动手修改

**自我检查问题**：我的"根因"有日志/中间产物证据吗？还是只是从最终输出反推的猜想？我有没有把"相关现象"当成"因果"？

**红线**：禁止跳过数据流追踪直接修改（呼应 .claudecode-rules.md §7.1"修改前必须先分析"、§8.1"Debug 必须分析根因"）。

---

### 原则 8：修改触发条件，而非修补结果

**一句话**：修复应该让破坏步骤在错误场景**根本不执行**，而不是在破坏发生后加"恢复"代码。

**案例**：Fix 1 修改空值模式的**触发条件**（`summary_cell_idx == 0` 时 continue，3 行），而不是在空值模式破坏合计行之后再加"检测被破坏的合计行并恢复"的补丁。事后恢复型补丁脆弱：管线顺序或输入特征一变，破坏形式变化，恢复逻辑就失效。

**AI 执行流程**：

1. 定位到"输出被破坏"的步骤后，向上游追溯：是哪个条件判断让它执行了？
2. 修改那个条件判断，使破坏步骤在错误场景中根本不执行
3. 判定标准：修复后，错误场景的日志中该破坏步骤不再出现
4. 若破坏步骤的触发条件无法区分对错场景 → 说明条件粒度不够 → 回到原则 4 收紧条件

**自我检查问题**：我的修复是"让坏事不发生"还是"坏事发生后擦屁股"？

## 三、强制工作流与产出物

抽象原则无法验证 AI 是否遵守；强制产出物可以。修改文档识别/表格后处理代码时，以下报告**必须写入对话**，不许用"已检查"三个字替代。

### 3.1 修改前：分析报告（必须产出）

1. **数据流定位报告**：异常引入的确切步骤（管线中哪一步把输入变成了错误输出），附中间产物证据（middle_json 片段、日志行）
2. **路径矩阵**：待修改函数的全部调用链 + 每条路径的触发条件 + 对应的测试文档

### 3.2 修改中：编码约束

- 遵守原则 2（custom/ 隔离）、原则 3（无特例）、原则 4（强约束启发式）
- 改动最小、可独立回滚

### 3.3 修改后：验证报告（必须产出）

1. **值集合三层对比**（多出/丢失/位移）+ 每个差异的解释
2. **当前文档对比**：当前文档修改前后输出逐差异对比
3. **路径覆盖标注**：每条路径标注"已测试/未覆盖（原因）"
4. **影响范围检查**（跨文档类型反向验证）：改动若为某类文档（如资产负债表）做的适配，必须反向验证**其它文档类型**（如发票）不被误伤。枚举改动影响的值/标签，区分两类——**唯一标签**（分区标题/列标题，仅出现一次，去重=正确"复制"拦截）与**可重复值**（单位「吨」/税率「免税」/税额「***」，可合法多次出现，去重=错误"丢失"）；两类各给一个用例：正向（目标场景被修复）+ 反向（可重复值仍能被放置/恢复）

## 四、反面案例库

每个案例给出【AI 识别特征】——AI 写代码时对照该特征，识别自己是否正在犯同样的错误。

### 案例 1：空值模式破坏干净合计行

- **现象**：合计行重复出现"2148"（原则 1 多出违例），"合计"从列 0 移到税率列（位移违例）
- **错误做法**：空值模式对**所有**"孤立合计格"执行重组，未区分"合计已标准"与"合计位置异常"
- **识别特征**：修改的函数对所有输入无条件操作，入口没有 guard clause
- **正确做法**：入口加 `if summary_cell_idx == 0: continue`（[table_utils.py:1196](../../../mineru/utils/custom/table_utils.py#L1196)），标准位置直接跳过
- **教训**：原则 8

### 案例 2：OCR 拆分字符丢表头

- **现象**：TH 行 `<th></th>` 空列，"金额"标签丢失（原则 1 丢失违例）
- **错误做法**：`ocr_header_labels` 用完整关键词匹配（`h in _INVOICE_HEADER_KEYWORDS`），OCR 拆出的单字"金"/"额"匹配失败即丢弃
- **识别特征**：匹配条件只有"完整命中"，没有对"部分命中/可合并"的容错
- **正确做法**：`_merge_split_header_chars`（[table_utils.py:2999](../../../mineru/utils/custom/table_utils.py#L2999)）先合并单字再匹配，合并条件三重约束（单字 × 单字 + 结果 ∈ 词典）
- **教训**：原则 4 + 原则 7（根因是 OCR 拆分，不是 VLM 非确定性）

### 案例 3："合计"关键词检测误触发

- **现象**：普通数据行因文本含"合计"被误判为汇总行，行结构和值列错乱
- **错误做法**：用宽泛关键词"合计"作为汇总行检测条件
- **识别特征**：检测条件是可误匹配的宽泛关键词，没有结构性/数值性佐证
- **正确做法**：改为数字位数启发式（汇总行有特定的数值形态），并与位置结构联合判断
- **教训**：原则 4——"合计"关键词匹配在"必然正确条件"上说不通

### 案例 4：管道顺序覆盖 ¥ 修正

- **现象**：合计行 ¥ 值对齐到"金额"列的修复无效，输出仍是错误列
- **错误做法**：¥ 修正在 `extract_column_header_prefixes` 内做，随后的 `normalize_invoice_table` colspan 重排改变列索引使其失效
- **识别特征**：新增步骤只检查了"我的输出正确"，没检查"后续步骤会不会改变我的输出"
- **正确做法**：新增 `fix_summary_row_yen_position` 作为管道最终步骤（[vlm_middle_json_mkcontent.py:102-111](../../../mineru/backend/vlm/vlm_middle_json_mkcontent.py#L102-L111)）
- **教训**：原则 6

### 案例 5：测试文档集覆盖不足漏检

- **现象**：审计声称"输出不多不少"已修复，干净合计行的发票仍出现重复值
- **错误做法**：只测了合计行含 ¥ 值的发票——空值模式从不触发，与干净合计行的发票是不同路径
- **识别特征**：测试文档集是"看起来相同"的同类文档，而非按触发条件矩阵挑选
- **正确做法**：按触发条件维度（VLM 输出格式、合计行特征、税率列特征、图片尺寸）覆盖路径矩阵
- **教训**：原则 5

### 案例 6：去重仅同行精确匹配 → 全角/跨行标签被复制（2026-08 资产负债表）

- **现象**：资产负债表 `_middle.json` / `.md` / `content_list` 多出"递延税项："等全角分区标题（原则 1 多出·复制违例），如「固定资产净额」行「递延税项:」右侧行次列被多填「递延税项：」
- **错误做法**：OCR 补充去重只做「同行 + 精确匹配」（`ot == vt`），全角标点（`递延税项：` vs `递延税项:`）与跨行标签（`流动资产：` 填进 `货币资金` 行）逃过去重被复制
- **识别特征**：去重范围过窄——仅当前行、仅精确匹配，未做全角/半角归一化、未覆盖表头/分区标题行；默认「回填 = 恢复」，未先判「放置/复制」
- **正确做法**：去重按类型区分——文本类与「同行 + 表头行」规范化比对（复用 `_normalize_for_matching`），数值类保持同行精确比对；**不覆盖其它数据行**（单位「吨」、税率「免税」等可重复值应保留被放置进漏识别单元格的能力）；填充退化为「只放置新增信息」
- **教训**：原则 1（放置/移动/复制三语义）
